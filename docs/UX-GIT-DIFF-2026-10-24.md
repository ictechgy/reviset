# Git 흐름을 참고한 화면 구조 제안

상태: **구조 논의 기록 · B 중심 구현 승인** · 2026-10-24. 논의 후 사용자가 추천안의 네이티브 구현을 지시했다. 아래 자문과 HTML 검사는 구현 이전의 증거이며, 실제 네이티브 적용·검증 결과와 구분한다.

추천은 **큰 원문을 기본으로 두고, 버전 → 변경 목록 → diff로 이동하는 구조**다. 기본 화면은 B처럼 원문과 좁은 변경 목록을 보여주고, 버전 이력과 상세 근거는 필요할 때 연다. 기존의 밝은 중립색과 파란 강조색을 유지한다.

[A/B/C 직접 비교 시안](design/git-diff-review/index.html)은 외부 의존성이 없는 단일 HTML이다. 파일을 브라우저에서 열면 된다. 합성 문서·통합문서 예시이며 네이티브 앱의 기능 구현이나 실제 PDF 렌더가 아니다. 기본은 B이고, 위쪽 A/B/C 버튼으로 구조를 바꿀 수 있다.

세 모델 모두 종결 의견으로 `DESIGN VERDICT: RECOMMEND HYBRID`를 냈다. 다만 같은 조합을 뜻하지 않는다. 서로의 결과와 소유자의 사전 추천을 보지 않은 첫 의견이며, 최종안에 대한 공동 승인이나 구현 리뷰가 아니다.

| Claude | 현재 소스 발췌·제품 계약·실제 PNG 3장 | B의 원문 캔버스 하나에 읽기/비교/이력 보기를 두고, A의 직전→선택 동작을 결합 | 보기 구분이 또 다른 선택 부담이 될 수 있음 |

| Grok | 같은 범위의 텍스트·코드·화면 설명, 직접 이미지 확인 없음 | B의 큰 원문 + 비교 막대 하나 + A의 이력 서랍. C의 전체 화면 탭 전환에는 반대 | 이력·변경 목록의 발견 가능성을 보완해야 함 |

공통 의견은 원문 확대, 고정 분석 결과 칩, 중복 범위 정리, 내보내기/MCP 이동, 근거의 점진 공개, 두 버전 차이와 중간 변경 이력의 구분이다. Mac 문서에서 이벤트를 선택해도 넓은 조회 구간을 유지하자는 제안도 공통으로 나왔다.

원문 의견을 대조하며 두 가지를 교정했다. Devin이 Mac Compare에 VersionBar가 함께 쌓인다고 본 부분은 실제 조건과 다르므로 진단에서 제외했다. Grok의 MCP 검증 제안 중 UI에서 고른 보고서 ID가 설정 복사만으로 MCP에 고정된다는 해석도 채택하지 않았다. 현재 MCP 설정은 프로젝트 범위이고, 클라이언트가 응답의 고정 보고서 ID를 이어 사용해야 한다.

실제 호출은 3회, 재시도 0회다. 새 version/help 확인, 도구 비활성화, 입력 보안 검사, 종료 코드와 종결 의견을 확인했다. 원문 stdout/stderr, argv, 입력·출력 SHA와 별도 의견 목록은 로컬 `.omx/artifacts/git-diff-ux-20261024/result-index.json`에 연결되어 있다. 이 기록은 공개 배포 문서에 포함되지 않는 로컬 증거다.

## 세 시안의 차이

| 안 | 기본 배치 | 장점 | 비용 |
| --- | --- | --- | --- |
| A · 버전 → 변경 → diff | 버전 목록 / 변경 목록 / 원문 비교 | Git 클라이언트처럼 이력과 변경의 관계가 선명함 | 세 열을 열면 수백 페이지 원문과 넓은 시트가 좁아짐 |
| B · 원문 중심 · 추천 기본값 | 좁은 변경 목록 / 큰 원문, 버전 선택은 팝오버 | 비교 작업을 계속하면서 원문을 크게 읽을 수 있음 | 이력 진입 버튼과 현재 조회 방식이 잘 보여야 함 |
| C · 검토 단계 | 버전 선택 → 변경 검토 → 원문 확인 | 처음 쓰는 사람에게 한 번에 한 질문을 제시함 | 목록과 원문 사이를 왕복해야 함 |

이 시안의 C는 단계 분리의 비용을 비교하기 위한 예시다. Claude의 같은 캔버스 안 보기 전환이나 Devin의 작업 모드 제안을 그대로 구현한 것은 아니다. A/B/C 모두 세 모델의 검토 후 작성한 소유자 측 비교 시안이며, 모델들이 이 HTML을 직접 검수했다고 표현하지 않는다.

## 추천 구조

```text
프로젝트 · 고정 분석 결과 칩                          가져오기 · 메뉴
조회 v1 → v5     [두 버전 차이 | 중간 변경 이력]       변경 목록 토글
──────────────────────────────────────────────────────────────────
변경 목록        이전 v2 · p.12       이후 v3 · p.14
                 원문 PDF             LibreOffice 변환 PDF
선택 변경        큰 원문 비교 / 추출 텍스트 diff
                 추정·확인 불가 등 선택한 변경의 주의 사항
──────────────────────────────────────────────────────────────────
                 이전/다음 변경 · 페이지/주소 이동 · 확대 · 근거
```

- **기본 동작:** 최근 가져온 버전과 그 직전을 비교한다. 버전 목록에서 vN을 고르면 직전→vN을 보여준다. v1은 원문 하나를 읽는다. 임의 A/B 선택은 계속 제공한다.
- **범위는 한 번씩:** 조회 구간은 비교 막대에, 현재 원문의 이벤트 쌍은 원문 헤더에 표시한다. 둘이 다르면 `구간 안 변경`임을 짧게 밝힌다. 이벤트 선택으로 조회 구간·목록 위치를 교체하지 않는다.
- **큰 원문:** B의 변경 목록은 열어 두고, 이력은 팝오버/서랍으로 연다. 집중 모드는 변경 목록도 접는다. 고정 보고서 칩과 선택 변경의 관측 공백·추정 표시는 남긴다.
- **근거:** 인용·출처·물리 주소는 선택 변경에 붙인다. 긴 전체 한계, 전체 해시, 대응 수정은 상세 보기나 메뉴에서 연다. 내보내기는 행동으로, MCP는 `AI 도구 연결`로 찾는다.
- **조회 방식:** `두 버전 차이`와 `중간 변경 이력`을 분명히 구분한다. 처음에는 별도 읽기/비교/이력 전체 화면을 강제하지 않는다. 한쪽 원문 보기는 캔버스의 보기 옵션으로 둔다.

현재 HTML은 비교를 위한 범위 설명과 시안 전환 머리말을 포함하므로, 최종 네이티브 도구막대 높이의 목표 화면은 아니다. 위 추천 구조의 모든 동작을 구현한 것도 아니다. 특히 직전→선택 기본값, 단일 버전 읽기, 실제 페이지 이동·지연 썸네일은 후속 구현 대상이다.

## Git에서 가져올 개념

Git의 두 끝점 diff는 그 사이의 모든 중간 이벤트와 구분된다. 이 구분을 문서에도 적용한다. 예를 들어 값이 `100 → 120 → 100`이면 첫 버전과 마지막 버전의 값은 같지만 중간 변경은 두 번이다. 실제 쿼리 없이 중간 변경 개수를 표시하지 않는다. [Git diff 공식 문서](https://git-scm.com/docs/git-diff)

GitHub Desktop의 이력 → 변경 파일 → diff 흐름을 버전 → 변경 페이지/시트 → 원문으로 옮길 수 있다. 추출 텍스트에는 unified/split diff를, 문서에는 실제 원문 비교를 제공한다. [이력 보기](https://docs.github.com/en/desktop/making-changes-in-a-branch/viewing-the-branch-history-in-github-desktop), [변경 검토와 diff 보기](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop)

Reviset의 버전 순서는 가져올 때 정한 원문 발생 순서다. Git 저자·커밋 시각·브랜치·스테이징·checkout·merge 조작은 추가하지 않는다. 분석 시각을 원본 수정 시각처럼 보이게 하지 않는다. 페이지 split/merge 대응은 Git 브랜치 병합과 별개다.

## 문서·통합문서·MCP 계약

- PDF 원문, Office에서 변환한 PDF, 구조 보기, OCR 추정의 출처를 구분한다. 취소선·가림·드러남은 표시 상태 관측이다. 확인 불가 페이지를 의미상 삭제로 칠하지 않는다.
- 페이지 p.12→p.14처럼 대응이 달라지면 실제 양쪽 페이지를 표시한다. 수동 탐색으로 근거를 벗어났다면 선택 변경으로 돌아오는 경로를 제공한다.
- 통합문서는 `예산!C2 → 예산!C3`의 물리 주소, 원문 수식, 저장값을 따로 읽는다. 행 대응은 추정이며 수식을 재계산했다고 표시하지 않는다. 빈칸·0·빈 문자열·미지원·조회 실패를 구분한다.
- 수백 페이지 썸네일과 변경 목록은 필요한 범위부터 읽는다. 목록 페이징만으로 전체 엔진 메모리가 일정하다고 약속하지 않는다. 대형 코퍼스 성능은 별도 측정이 필요하다.
- Mac의 PDFKit/AppKit 호스트와 Windows WPF 원문·그리드 인스턴스를 유지한다. 패널/언어/보기 변경으로 보고서, 페이지·셀, 확대·수동 스크롤을 초기화하지 않는다. HTML 시안은 네이티브 앱을 웹 셸로 바꾸자는 제안이 아니다.
- 보고서 칩은 집중 모드에서도 남는다. 내보내기는 선택한 고정 보고서 ID를 사용한다. MCP 설정은 프로젝트 범위이며 UI의 보고서 선택을 자동으로 고정하지 않는다. `latest` 응답에서 얻은 고정 ID를 이후 읽기·인용에 사용한다.
- 레이아웃·언어 선호는 보고서와 MCP 데이터에 넣지 않는다. 기존 수정 가능 조건, CAS, 부분 실패·취소·확인 불가 표시를 보존한다. Windows OCR·Office 변환의 기존 미지원 범위를 유지한다.

## 도입 순서와 확인할 과제

1. Mac 문서·통합문서·Windows의 조회 구간/선택 이벤트 모델과 용어를 맞춘다.
2. 보고서 칩·비교 막대·행동 메뉴로 상단을 정리하고 인스펙터 중복을 줄인다.
3. B를 기본으로 두고 A의 이력 탐색을 접히는 패널로 제공한다. 기존 사용자 레이아웃을 버전 있는 선호 값으로 이전한다.
4. 이전/다음 변경, 뒤로 가기, 페이지/주소 이동, 텍스트 diff, 좁은 창·높은 배율을 다듬는다.

이 순서는 구현 제안이다. 동작 변경은 기존 계약 테스트와 실제 네이티브 검증을 거쳐야 한다. 사용성 확인 과제는 최근 버전 비교, `100→120→100`의 두 질문 구분, 수백 페이지에서 변경으로 이동 후 복귀, 이동 행의 주소·저장값·수식 설명, 이전 보고서 고정 후 내보내기다. 보고서/조회 구간/선택 이벤트/뷰포트 보존, 영어·한국어, Mac VoiceOver·Windows Narrator·키보드와 높은 배율은 각각 검증한다.

이번 확인 범위는 합성 HTML 시안의 브라우저 상호작용과 정적 배치다. 1440×1050 및 1024×900에서 30개 검사를 통과했고, 별도 새 세션에서 B 기본 진입을 확인했다. 버전 쌍 검증, 조회 구간/선택 이벤트 구분, 집중 모드의 보고서 유지, 텍스트 diff, 확인 불가·가림의 중립 표시, 통합문서 물리 주소와 저장값, 단계형 뒤로 가기, 근거 서랍 복귀, IME 입력 중 단축키 억제를 포함한다. 로컬 원본 증거와 HTML·QA·캡처 해시는 `.omx/artifacts/git-diff-ux-20261024/prototypes/manifest.json`에 있다.
